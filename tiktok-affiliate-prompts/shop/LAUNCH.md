ระบบพร้อมแล้วในเชิงโค้ด (ผ่านเทสต์ 85 ข้อ + ทดสอบบน workerd จริง 13 ข้อ)

## 0) สิ่งที่ต้องรู้ก่อน (สำคัญ)
พร้อมเพย์ **บัญชีบุคคล** ไม่มี webhook แจ้งเงินเข้า (ต่างจากบัญชี merchant/เกตเวย์)
ระบบนี้จึงทำงานแบบร้านออนไลน์ทั่วไป: ลูกค้าสแกน QR → แจ้งโอน (แนบสลิป) → ร้านกดอนุมัติ → ส่งลิงก์ให้ลูกค้าอัตโนมัติ
- ถ้าอยากให้ **ตรวจสลิปอัตโนมัติ 100%** ให้ซื้อคีย์ผู้ให้บริการตรวจสลิป (ดูข้อ 5) — ไม่ซื้อก็ขายได้ แค่ต้องกดอนุมัติเอง
- ถ้าอยากได้ระบบที่ "เงินเข้าอัตโนมัติไม่ต้องกดอะไรเลย" ต้องใช้ Payment Gateway (ระบบนี้รองรับด้วย: `PAYMENT_PROVIDER=omise`)

⚠️ **Resend มี MX/TXT ที่ซับโดเมน `send`** ส่วน **Email Routing ใช้ MX ที่ root (`@`)** — คนละชื่อกัน จึงอยู่ร่วมกันได้ (อย่าตั้งผู้รับเมลที่ root สองเจ้า)

✅ **เพิ่ม TXT `_dmarc` แล้ว (16 ต.ค. 2026)** — ค่าที่ใช้จริง **`v=DMARC1; p=none;`** (TTL 300) ที่ **Cloudflare → โซน `kopwang.com` → DNS → Records** · ตรวจซ้ำแล้ว 4 ทาง (`dig +short TXT _dmarc.kopwang.com @1.1.1.1`, `@8.8.8.8`, DNS-over-HTTPS, nameserver ต้นทาง) เห็นค่าเดียวกันหมด · `p=none` = เฝ้าดูอย่างเดียว ยังไม่บล็อกอีเมลใด ๆ
→ ขั้นถัดไป: หลังส่งเมลจริงสักพักและไม่มีอีเมลตกหล่น ค่อยขยับเป็น `p=quarantine` แล้ว `p=reject` (วิธีตรวจผล + การเปิดรายงาน `rua` อยู่ใน **DOMAIN.md ข้อ 8**)

2. **เลขถูกปิด** → ต้องรู้ “ประเภท” (พร้อมเพย์บัตร ปชช. `NATID` / เบอร์ `MSISDN` / e-Wallet / บัญชีธนาคาร `BANKAC`) แล้วเทียบเฉพาะ **ท่อนตัวเลขที่ยังมองเห็น (รวมกัน ≥ 4 หลัก โผล่เรียงตามลำดับ)** — พร้อมเพย์บัตร ปชช. จึงใช้ท่อน `0201` ของเบอร์มือถือไม่ได้
ถ้าผู้ให้บริการยืนยัน `matchedAccount` ให้ (ลงทะเบียนบัญชีรับเงินไว้กับคีย์) สลิปที่ไม่บอกเลขผู้รับเลยก็ยังอนุมัติได้
ไม่ครบข้อไหน → ค้าง `reported` + เก็บเหตุผล (`verify_note`) + นับครั้งที่ลอง (`verify_attempts`) ให้หลังบ้านเห็น — **ห้ามใช้ระบบนี้แทนการไม่ตรวจเลย** ควรทดสอบด้วยสลิปจริงก่อนเปิดขาย

### 5.11) ตรวจว่า “อีเมลจริง” ผ่าน DMARC จริง (SPF/DKIM)
ดูเรคคอร์ด DNS อย่างเดียว **ยังไม่ยืนยัน** ว่าอีเมลที่ส่งถึงกล่องปลายทางผ่านจริง — ใช้ 2 เครื่องมือนี้:
```bash
cd shop
node tools/send-test-email.mjs                 # ส่งอีเมลทดสอบ 1 ฉบับ (อ่านคีย์จาก .secrets/ — ไม่พิมพ์คีย์ออกจอ)
# → เปิดอีเมลในกล่อง → ⋮ → “แสดงต้นฉบับ / Show original” → ดาวน์โหลด/บันทึกเป็น received.eml
node tools/check-email-auth.mjs received.eml   # ถอดลายเซ็น DKIM เอง + วิเคราะห์ SPF/DMARC + alignment
```
- ต้องเห็นทั้งหมด: `DKIM-Signature: d=kopwang.com` → `body hash (bh): OK` · `ลายเซ็น (b): OK` · `spf=pass` · `dmarc=pass` · ปิดท้าย **`RESULT: PASS`** (exit code 0)
- ⚠️ **อีเมลเป็นของจริงทุกฉบับที่ร้านส่ง** (ใบเสร็จ/ของแถม) → ใช้ต้นฉบับของใบเสร็จจากกล่องลูกค้ามาตรวจก็ได้ ไม่ต้องส่งฉบับทดสอบซ้ำ
- ⚠️ ถ้าส่งไม่ออกด้วย `401 API key is invalid` → คีย์ที่ใช้อยู่เก่า (เช่นไฟล์ `.dev.vars` ของโหมด workerd) ให้รัน **`node tools/sync-dev-vars.mjs`** เพื่อดึงคีย์/`MAIL_FROM` ล่าสุดจาก `.secrets/` แล้วรีสตาร์ท · **production ไม่ได้อ่าน `.dev.vars`** ใช้ Sites → Secrets เท่านั้น
- ⚠️ ถ้าไม่ได้ตั้ง `MAIL_FROM` ระบบจะใช้ `onboarding@resend.dev` ซึ่ง Resend ยอมให้ส่ง **เฉพาะอีเมลเจ้าของบัญชีเท่านั้น** → อีเมลถึงลูกค้าจะถูกปฏิเสธ (`403 You can only send testing emails to your own email address`)
- ตัวตรวจ **ไม่เชื่อหัว `Authentication-Results` อย่างเดียว**: ถ้าในอีเมลมี DKIM-Signature มันจะ ถอดลายเซ็นเองด้วยกุญแจสาธารณะจาก DNS (`resend._domainkey.kopwang.com`) — ถ้าข้อความถูกแก้ระหว่างทางจะขึ้น FAIL ทันที (มีเทสต์ตัวเองยืนยันทั้งกรณีผ่านและกรณีถูกแก้ รันอยู่ใน `node test.mjs`)
- ℹ️ คีย์ Resend ของร้านเป็นแบบ **ส่งอย่างเดียว** → ดึงสถานะ delivered/bounced ผ่าน API ไม่ได้ (401) ให้ดูที่ resend.com → Emails แทน · `--to=` ส่งไปอีเมลอื่นได้ · `--id=<id>` ดูสถานะฉบับที่ส่งไปแล้วโดยไม่ส่งซ้ำ
